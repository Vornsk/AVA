# 05 · 취약점 목록 (Findings)

> 사이드바 **결과 > 취약점** · 소스 `frontend/src/pages/Findings.tsx` · 전체 초기화는 리더 전용

도출된 취약점(finding)을 확인하고 **검토 상태를 관리**하는 페이지입니다. 각 finding의 증적을
펼쳐 보고, 상태머신에 따라 처리합니다. 요구사항 §5.4·FR-4.x에 대응합니다.

## 화면 구성

- **필터 바** — 심각도별 카운트 칩(high/medium/low/info 토글), 상태 드롭다운, `LLM 오탐 숨기기`
  (LLM이 오탐 표시한 항목을 보기에서만 숨김·데이터 유지), 표시/전체 수
- **취약점 테이블** — ID · 취약점명 · 심각도 · 대상(host·method·path) · 파라미터 · 탐지기(VulnDef) ·
  점검항목 배지 · 상태. **심각도순(high 먼저) → 최신순** 정렬
- **증적 확장 (행 클릭, FR-4.2)** — LLM 판정 배지+근거, 재현 요청, 증명 응답(HTTP 코드,
  **민감값 마스킹**) `pre` 블록

## 검토 상태머신 (FR-4.4)

```
신규 → 검토중 → 확정 → 보고
          ├→ 오탐 (종료)
          └→ 보류 → 검토중
```

상태 전이는 **낙관적 락(FR-1.3)** — 다른 사용자가 먼저 수정하면 409 충돌 표시 후 폴링으로 최신화.
각 행에 버전(`v{n}`) 표시.

## LLM 오탐 트리아지 (FR-3.3)

스캔 시 `LLM 오탐 검토`를 켜면 각 finding에 `real / false_positive / uncertain` 판정과 근거가
**주석**으로 붙습니다. ⚠️ **상태는 자동으로 안 바꿈(HITL)** — 약한 모델이 진짜 취약을 오탐 판정해도
숨기지 않도록 설계. 사용자가 `LLM 오탐 숨기기` 필터로 직접 판단합니다.

### 프롬프트는 detector 별로 자동 생성된다 (이슈 #54)

트리아지 프롬프트가 detector 종류와 무관한 상수 하나였습니다. 그래서 detector 의 맹점을
트리아지도 그대로 가져 서로의 실수를 잡지 못했습니다 — #49 벤치의 오탐 5건이 전부 그 사례로,
`reflected-input` 도 트리아지도 응답 Content-Type 을 보지 않아 `text/plain` 반사를 XSS 로 봤습니다.

지금은 `llm.reviewPrompt(detectorID)` 가 네 조각을 조립합니다:

1. 공통 판정 기준 — `real`(확증) / `false_positive`(반증) / `uncertain`(증적 부족)
2. 응답 메타데이터 규칙 — `content_type` 이 마크업을 렌더링하는 타입인가 (`finding.ContentType`)
3. **detector 별 힌트 20종** — 반드시 `REAL when …` 과 `FALSE POSITIVE when …` 을 함께 담습니다
4. 규제 맥락 — 산출물이 KII·전자금융 제출 증적이므로 **정탐을 지우는 쪽이 더 비쌉니다.**
   근거를 지목할 수 없으면 `false_positive` 가 아니라 `uncertain` 입니다

> ⚠️ **한쪽 조건만 적힌 힌트는 모델을 그쪽으로 민다.** 오탐 조건만 나열한 첫 판본은 qwen2.5:3b 가
> `reflected-input` 을 통째로 오탐 처리하게 만들어 **정탐 6건을 지웠습니다**. 판단 프롬프트가 겪은
> 실패와 같은 모양입니다(기준 없이 쓰니 전건 차단). `TestTriageHintsAreSymmetric` 이 이 회귀를 막습니다.

**모델 선택 — 태스크마다 다릅니다.** 판단(Judge)은 `qwen2.5:3b` 를 권하지만(7b 는 false-allow),
**트리아지는 7b 가 필요합니다.** 3b 는 오탐을 줄이면서 정탐도 8건 지웠고, 7b 는 정탐 손실 0건이었습니다.
실측표는 [scan-groundtruth/README](scan-groundtruth/README.md) 2026-08-24 절.
