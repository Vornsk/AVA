proxy-poc · 문서

proxy-poc — LLM 기반 웹 취약점 진단 도구 (CyberGuard Vulnerability Engine)

Go(goproxy) MITM 프록시 엔진을 코어로, 그 위에 MCP 오케스트레이션 계층과 React 웹 GUI를 얹은 LLM 기반 웹 취약점 진단 도구입니다. 프론트를 go:embed로 넣어 단일 실행 바이너리로 배포됩니다. 주요정보통신기반시설·전자금융 규제 점검항목표에 맞춘 자동 진단 → 도출리스트/점검결과표(xlsx) → 이행점검까지 전 워크플로우를 커버합니다.

구성포트역할
프록시:8080HTTPS 가로채기(MITM) + 스코프 강제 + 인증 주입 + 판단 파이프라인 + 마스킹 + 공격면 캡처(런타임 on/off·상태 조회)
MCP:8765외부 LLM 에이전트/번들 클라이언트가 라이브 프록시를 조회·제어 (StreamableHTTP)
웹 GUI:8090진단 현황·취약점·증적·커버리지·리포트 (다크 기본, 테마 토글)

한눈에

  • 탐지기 25종(내장 23 + 외부도구 2) — XSS 3형태·SQLi 3종·인젝션 계열(cmd/SSRF/XXE/SSTI/LDAP/SSI)·접근통제·설정 점검. 규제 점검항목에 매핑돼 수동 항목 최소화
  • 판단 파이프라인 — 스코프(hard) → Rule(결정론) → LLM(애매한 요청만) → 전송+캡처. 스코프 밖으로 아무것도 내보내지 않음
  • 자동 공격면 탐색 — 링크·폼·JS 번들을 따라가는 크롤러(정적/헤드리스 옵트인) + 프록시 수동 캡처(런타임 캡처 on/off·상태 API/MCP)
  • 증적 기반 — 각 finding에 재현 요청·증명 응답(민감값 마스킹)·상태코드
  • 규제 산출물 — 도출리스트 11컬럼 xlsx(+증적 시트) · 점검결과표(양호/취약/미점검) · 감사 CSV
  • 멀티테넌시·RBAC·영속화 — 프로젝트별 격리 프록시, 리더/수행원 권한, bcrypt 로그인, 인증정보 AES-256-GCM 암호화, 재시작 넘어 데이터 유지

빠른 실행

프론트를 먼저 빌드해야 합니다(출력이 Go 바이너리에 embed됨):

cd frontend
npm install            # 최초 1회
npm run build          # → backend/internal/webui/dist (embed)

backend/internal/webui/dist는 빌드 산출물이라 커밋되지 않습니다. go build 전에 반드시 위 프론트 빌드를 먼저 수행하세요. 건너뛰면 pattern all:dist: no matching files found 로 컴파일이 실패합니다.

백엔드 빌드 & 실행:

cd proxy-poc/backend
go build -o proxy-poc.exe ./cmd/proxy    # 프록시(:8080) + MCP(:8765) + 웹(:8090)
./proxy-poc.exe                          # 최초 실행 시 ca.crt/ca.key 생성

웹 GUI: http://127.0.0.1:8090 — 데모 계정 leader / leader123, analyst / analyst123. 프록시로 트래픽을 흘려 공격면을 채운 뒤 스캔합니다(상세는 docs/00-아키텍처.md 참고):

curl.exe -sk -x http://127.0.0.1:8080 "https://httpbin.org/get?user=admin&password=secret" -o NUL

빌드·CA 신뢰·브라우저 프록시 경유·설정(YAML)·테스트 등 전체 절차는 docs/00-아키텍처.md에 정리돼 있습니다.

현황 (요약)

전 워크플로우가 end-to-end로 도는 잘 설계된 PoC입니다. 아키텍처(멀티테넌시·영속화·RBAC· 암호화·증적·커버리지)는 견고하며, 인젝션 계열 자동화(SQLi·XSS·cmd·SSRF·XXE·SSTI·LDAP·SSI)는 실앱(DVWA + 자체 vulnlab)으로 정탐 검증했습니다. 정밀도·커버리지·LLM 엔진(대형 모델 연동)·실운영 하드닝은 계속 고도화 중입니다. 자세한 성숙도·로드맵은 docs/00-아키텍처.md의 "성숙도 & 다음 단계"를 참고하세요.

민감 파일(공유/커밋 금지): ca.key, secret.key, users.json, projects.json. local.config.yaml은 PC 전용(키 보관), project.config.yaml은 공유 가능(스코프·룰).

1. 설계 배경 & goproxy 선택

상위 폴더(../)에 세 개의 한글 설계 문서가 있습니다:

문서목적
취약점진단도구_요구사항_아키텍처_정의서.md전체 요구사항 & 아키텍처
프록시_엔진_전략_비교분석.md프록시 엔진 전략 비교(풀커스텀/세미커스텀/기성)
취약점진단도구_프록시 전략 및 추진 계획.md프록시 결정 + 추진 계획

문서 권고: *세미커스텀* 프록시 — 검증된 TLS 엔진을 재사용하고 판단 로직만 직접 구현. 1순위는 mitmproxy, goproxy는 단일 바이너리 배포가 꼭 필요해질 때 대비.

실제 선택(의도적 편차): 배포가 단일 Go 바이너리로 기우는 만큼 goproxy를 코어로 직접 검증. mitmproxy 폴백은 열어둠.

두 계층 (경쟁 아님)

┌─────────────────────────────────────────────┐
│  오케스트레이션 계층 (LLM 주도) = MCP        │  ← 공격면 조회 / 스코프·스캔 제어
├─────────────────────────────────────────────┤
│  코어 엔진 (goproxy)                          │  ← 가로채기 + 스코프 + 마스킹 + 공격면
└─────────────────────────────────────────────┘

판단 파이프라인(스코프/마스킹)은 가로채는 지점에서 인라인으로 돌아 스코프 밖으로 아무것도 안 나갑니다. MCP는 그 위에서 LLM이 조회·제어하는 계층.

왜 Burp가 아니라 Go-native MCP인가 (중요 발견)

당초 Burp의 공식 MCP 확장을 붙일 계획이었으나 이 머신에서 실행 불가입니다. Burp MCP 확장(JVM/Netty)이 기동 시 failed to create a child event loop로 죽습니다. 근본 원인:

  • JVM의 NIO Selector가 내부 self-pipe를 AF_UNIX(유닉스 도메인 소켓) 로 만드는데,

이 머신은 AF_UNIX connect가 전역으로 실패합니다(connect: Invalid argument). 번들 OpenJDK와 별도 Go 프로그램 양쪽에서 재현. listen/bind는 되고 connect만 실패 — 보안 소프트웨어/Winsock-LSP 간섭(보안 워크스테이션의 의도적 하드닝 추정).

결론 & 교훈: 이 폐쇄/보안 환경에서 JVM-NIO·AF_UNIX 기반 IPC는 불안정. Go + TCP가 더 견고합니다(Go의 Windows 런타임은 IOCP+TCP를 쓰고 AF_UNIX를 안 씀). goproxy 선택을 강화하는 근거. Burp MCP를 나중에 쓰려면 머신을 고치거나(netsh winsock reset+재부팅) 다른 호스트에서 실행해야 합니다.

2. 판단 파이프라인

스코프(host+path) → [설정된 스테이지: Rule → LLM] → (전송 + 캡처)

  • 스코프(FR-2.1): 화이트리스트 밖 host/path는 하드 차단. 프록시·크롤러·스캔 모두 공유.
  • Rule 스테이지(FR-2.2): 결정론적 룰로 위험/파괴적 요청을 전송 전 차단(logout·DELETE·

삭제성·admin·결제확정). recon_allow로 접근통제 점검 시 관리자 경로 recon만 허용.

  • LLM 스테이지(§5.2): Rule이 llm으로 표시한 상태변경 요청을 LLM이 allow/block 판단.

입력 토큰 최소화(정규화 path + 파라미터 키만), 판정 캐싱·로깅. 프로바이더 교체형 (mock|ollama|anthropic|openai).

  • 캡처 제어: 공용 프록시(:8080)의 엔드포인트 캡처는 런타임에 on/off 할 수 있습니다

(GET /api/proxy 상태 · POST /api/proxy/capture 토글 · MCP proxy_status/set_capture, 리더 전용·감사). 프로세스·스코프·인증·판단은 불변, 테넌트 전용 프록시는 미영향(격리 유지). 상세 → 03-정찰.

판정 기록은 룰 제안 페이지에서 룰 이관 후보의 근거가 됩니다.

3. 자동 진단 (탐지기 25종 + 데모)

내장 23종 + 외부도구 2종. 규제 점검항목표에 매핑됩니다(→ 커버리지).

  • 기본/정보노출: security-headers(보안헤더 누락) · sensitive-data(한국형 RRN/카드

[Luhn 검증]/여권/계좌[날짜·전화 오탐 배제])

  • XSS 3형태: reflected-input(반사형, 컨텍스트 인식 — 실행 가능 위치만) ·

stored-xss(저장형, 고유 마커가 클린 재조회에 반사되면 확정 · 파괴적/옵트인) · dom-xss(source→sink 정적 힌트). DVWA xss_r/xss_s/xss_d 실앱 검증 완료

  • 접근통제: idor(수평/미인증노출) · privesc(수직 권한상승) — 차등 분석, 동적 콘텐츠

정규화로 견고

  • 인젝션(공격형): sqli(에러) · sqli-blind(불린) · sqli-time(시간지연, 2회 확증) ·

path-traversal · open-redirect · cmd-injection · ssrf · ssti · xxe · ldap-injection · ssi-injection · csrf(수동적 분석) · file-upload(파괴적, 옵트인). 쿼리·폼바디·JSON(중첩 포함) 모두 주입

  • 설정 점검: cookie-security(쿠키 속성) · http-method(위험 메서드) · dir-indexing
  • 외부 도구(FR-3.4): openssl-tls · sslscan (없으면 우아하게 skip)
  • 가드레일(FR-3.2): 파괴적 탐지기 기본 제외(allow_destructive 옵트인) · rate-limit ·

safe-mode · 긴급 kill-switch

  • 증적(FR-4.2): 각 finding에 재현 요청 + 증명 응답 스니펫 + 상태코드(마스킹)
  • 비동기 잡(FR-3.8): 진행률·일시정지·재개·취소

각 탐지기는 정탐 + 오탐 회피 대조 테스트로 검증합니다(반사 XSS는 실행 컨텍스트만·textarea/ 인코딩 반사 무발동, 저장형은 반사형만인 경우 무발동, DOM은 sink만이면 무발동, 카드는 Luhn 유효만, CSRF는 토큰 있으면 무발동). 인젝션 계열은 실앱(DVWA + 자체 vulnlab)으로 정탐 검증했습니다.

5. 멀티테넌시 (§5.1, Phase 2 완료)

프로젝트별 전용 프록시를 자체 포트에 기동. scope·endpoints·auth·traffic 4종 모두 인스턴스 격리 → 두 프로젝트를 동시에 진단해도 교차오염 0. 공유는 stateless한 판단 파이프라인·마스킹뿐. 자세한 조작은 프로젝트 문서를 참고하세요.

6. 프로젝트 구조

루트는 backend/(Go)와 frontend/(React) 두 갈래. 프론트는 backend/internal/webui/dist로 빌드되고 Go가 //go:embed → 런타임 단일 바이너리.

8. 브라우저 테스트 (실제 Edge/Chrome 프록시 경유)

  1. 프록시를 한 번 실행해 ca.crt 생성.
  2. CA 신뢰(현재 사용자 저장소, 관리자 불필요, 되돌림 가능). 보안 설정 변경이라 직접 실행:

``bash proxy-poc.exe -cert-status # 우리 CA가 신뢰됨? (지문 확인, 멱등) proxy-poc.exe -cert-install # 사용자 Root 저장소에 설치 proxy-poc.exe -cert-verify # 프록시 실행 중: 경유 HTTPS로 인터셉트+신뢰 확인 proxy-poc.exe -cert-uninstall # 완료 후 제거 ``

  1. 프록시를 가리키는 격리 브라우저 실행(시스템 프록시 변경 없음):

``bash & "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --proxy-server=http://127.0.0.1:8080 --user-data-dir=$env:TEMP\edge-proxytest --no-first-run --new-window https://example.com/ ``

보안: goproxy 내장 CA(개인키가 GitHub에 공개됨)가 아니라 자체 CA를 생성합니다. ca.key는 비공개.

9. 알려진 한계 — HTTP/2 다운그레이드

goproxy의 MITM은 ALPN에서 HTTP/1.1만 광고 → 가로챈 HTTPS는 전부 HTTP/1.1로 다운그레이드 (클라이언트↔프록시). 표준 웹앱 진단엔 문제없음(모든 요청/응답 가시·수정 가능). 미지원: HTTP/2 특화 테스트(h2 스머글링, HPACK), gRPC/h2-only API, HTTP/3(QUIC). 필요해지면 문서상 mitmproxy 폴백 트리거(h2/h3 지원).

10. 함정 (겪은 것들)

  • 8080 포트 충돌: Burp Suite 기본 프록시도 127.0.0.1:8080. Burp가 켜져 있으면 트래픽이

Burp로 감 → 프록시가 "빈" 것처럼 보임.

  • 좀비 프록시: 백그라운드 실행이 stale proxy-poc.exe를 남김 → 재시작 전 taskkill //F //IM proxy-poc.exe.
  • AF_UNIX 전역 고장(§1): JVM-NIO/AF_UNIX 기반 도구(Burp MCP 포함) 실패 → Go/TCP 선호.
  • 실행 중 exe 덮어쓰기 불가(Windows): 재빌드 전 프록시 종료.
  • 콘솔 한글 깨짐: 코드페이지 표시 문제일 뿐 파일은 UTF-8. 검증은 PYTHONIOENCODING=utf-8 등.
  • Git Bash 경로 변환: /로 시작하는 curl URL을 Windows 경로로 변환 → export MSYS_NO_PATHCONV=1.

11. 성숙도 & 다음 단계 (정직하게)

이건 전 워크플로우가 end-to-end로 도는 잘 설계된 PoC입니다 — 아키텍처(멀티테넌시·영속화· RBAC·암호화·증적·커버리지)는 견고합니다. 다만 탐지 정밀도·커버리지는 계속 고도화 중이며 실운영에는 다음이 더 필요합니다:

  • 탐지 정밀도 — 자체 vulnapp + DVWA-low + 자체 vulnlab에서 검증(XSS 3형태·cmd 실앱 확인).

오탐은 2차까지 개선(컨텍스트 인식 XSS·차등 정규화·Luhn·계좌 날짜/전화 배제·sqli-time 2회 확증). 저장형 XSS 전용 재검증 pass·SPA/REST(Juice Shop) 대응 등은 남음

  • 커버리지 — 자동 크롤러(BFS Explore + SPA 정적 JS 추출 + 헤드리스 옵트인) 있음. 인젝션 계열은

쿼리/폼/JSON 바디까지 자동화. 남은 수동 항목은 거래보안·모바일 정적분석·바이너리 계열

  • LLM 엔진 — 오탐 검토는 붙였으나 소형 모델(llama3.2:1b)은 부적합. Claude/대형 모델 + 페이로드 적응이 실제 가치
  • 운영 — JSON 파일 저장(실 DB 아님), 로컬 전용, 배포/모니터링 미비

로드맵(설계 문서): 0.설계검증(이 PoC) → 1.서버기반 → 2.프록시/recon → 3.스캔엔진 → 4.결과/리포트/이행점검 → 5.LLM 게이트웨이/오탐검토/배포 → 6.모바일 확장. 현재 0~4 및 5의 상당 부분 구현. 남은 큰 항목: 모바일(§6.2, 별도 툴체인), 실운영 하드닝.

  • Auth & Identities — 세션 주입 On/Off, 주입 쿠키/헤더, 등록된 진단 신원(수평/수직 접근통제 대조용)
  • 로그인 시퀀스 (세션 지속성, FR-2.5) — 긴 스캔 중 세션 만료 시 자동 재로그인 절차 설정.

로그인 URL·만료 표식(정규식, 있어야 활성화)·폼 필드·CSRF 토큰. 값은 마스킹, 저장은 리더 전용, 비밀번호는 응답 미노출·인메모리 주입기에만 반영

프록시 캡처 제어 (공용 :8080)

공용 프록시는 항상 켜져 있고, 엔드포인트 캡처(공격면 기록)만 런타임에 on/off 합니다 (프로세스·스코프·인증·판단 파이프라인은 영향 없음). 캡처를 끄면 트래픽은 그대로 통과하되 endpoints.json에 새 엔드포인트가 기록되지 않고, 다시 켜면 재개됩니다.

  • 상태 조회 GET /api/proxy — 리슨 주소·캡처 여부·스코프 호스트 수·누적 캡처 수·공격면 규모

  • MCP proxy_status(조회) · set_capture(토글, 리더) — 외부 에이전트용
  • 테넌트 전용 프록시(02-프로젝트)는 이 토글의 영향을 받지 않습니다(격리 유지)

GUI 연동 완료(이슈 #9) — 위 상태·토글은 정찰 페이지 좌측 프록시 도구 카드에서 바로 쓸 수 있고, API·MCP로도 동일하게 제공됩니다. (CA 설치는 OS 신뢰저장소 변경이라 웹에서 실행 불가 → 명령 안내로 제공)

스캔 / 자동화 진단 (Scan)

사이드바 진단 > 스캔소스 frontend/src/pages/Scan.tsx실행제어는 scan:run 권한

미설치 표시), 옵션 토글:

  • LLM 오탐 검토 — 각 finding을 LLM이 증적으로 검토·주석(상태는 안 바꿈, HITL)
  • 파괴적 포함 — file-upload 등 부작용 가능한 탐지기 포함(opt-in)
  • Scan Runs (FR-3.8) — 실행 목록(ID·상태·탐지기·건너뜀·진행률·findings·safe). 각 행에서

일시정지 / 재개 / 취소 제어(상태별 노출, 취소는 confirm). 상태 색상: 진행=blue·일시정지=amber· 완료=green·중단=muted. 2초 폴링

  • 가드레일 — Safe mode · Destructive opt-in · rate-limit(safe 500ms / 일반 150ms) · kill-switch
  • 페이로드 — 페이로드 버전, XSS 페이로드, 한국형 민감정보 패턴
  • 외부 도구 — openssl/sslscan 설치·버전 상태

취약점 목록 (Findings)

사이드바 결과 > 취약점소스 frontend/src/pages/Findings.tsx전체 초기화는 리더 전용

도출된 취약점(finding)을 확인하고 검토 상태를 관리하는 페이지입니다. 각 finding의 증적을 펼쳐 보고, 상태머신에 따라 처리합니다. 요구사항 §5.4·FR-4.x에 대응합니다.

화면 구성

점검항목 배지 · 상태. 심각도순(high 먼저) → 최신순 정렬

민감값 마스킹) pre 블록

검토 상태머신 (FR-4.4)

신규 → 검토중 → 확정 → 보고
          ├→ 오탐 (종료)
          └→ 보류 → 검토중

상태 전이는 낙관적 락(FR-1.3) — 다른 사용자가 먼저 수정하면 409 충돌 표시 후 폴링으로 최신화. 각 행에 버전(v{n}) 표시.

LLM 오탐 트리아지 (FR-3.3)

스캔 시 LLM 오탐 검토를 켜면 각 finding에 real / false_positive / uncertain 판정과 근거가 주석으로 붙습니다. ⚠️ 상태는 자동으로 안 바꿈(HITL) — 약한 모델이 진짜 취약을 오탐 판정해도 숨기지 않도록 설계. 사용자가 LLM 오탐 숨기기 필터로 직접 판단합니다.

각 후보: verdict(block/allow) · method·path · 적중 수 · 일관성 · 신뢰도 · 예상 절감 질의 수, draft rule(YAML) 미리보기, 경고(있으면). 룰로 채택(승인) 버튼(리더)으로 활성 룰셋에 반영

  • 활성 룰셋 — 현재 적용 룰 목록(위에서부터 우선, 첫 매칭). #·이름·action·methods·path·reason.

채택된 룰은 앞쪽에 prepend되어 영속화(rules.adopted.json)

  • LLM Decision Log — 프록시·진단의 모든 LLM 판정 기록. allow/block 필터, 캐시 적중률

(높을수록 룰 이관 효과 큼). 요청·판정·신뢰도·근거·모델·캐시 hit 표시

HITL(사람 개입) 설계
