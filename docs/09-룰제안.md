# 09 · 룰 제안 (Rule Advisor)

> 사이드바 **인텔리전스 > 룰 제안** · 소스 `frontend/src/pages/Advisor.tsx` · 룰 채택은 `rule:promote` (리더 전용)

LLM 판단 기록을 분석해 **반복·일관된 패턴을 결정론적 룰로 이관**하도록 추천하는 페이지입니다.
LLM 질의 비용을 줄이고 판단을 재현 가능하게 만듭니다. §5.6에 대응합니다.

## 화면 구성

- **룰 추천 후보** — 판단 로그가 시그니처별로 반복·일관되면(빈도≥2, 일관성≥70%) 룰 초안을 제안.
  각 후보: verdict(block/allow) · method·path · 적중 수 · 일관성 · 신뢰도 · 예상 절감 질의 수,
  draft rule(YAML) 미리보기, 경고(있으면). **`룰로 채택(승인)`** 버튼(리더)으로 활성 룰셋에 반영
- **활성 룰셋** — 현재 적용 룰 목록(위에서부터 우선, 첫 매칭). #·이름·action·methods·path·reason.
  채택된 룰은 앞쪽에 prepend되어 영속화(`rules.adopted.json`)
- **판단 프롬프트 정책** (이슈 #53) — 판단 스테이지의 보수성 선택. 프리셋 `strict`·`balanced`·
  `permissive` 칩 또는 커스텀 프롬프트(입력 시 프리셋보다 우선). 실제 적용될 system 프롬프트를
  그대로 미리보기로 보여준다. 저장은 리더(`llm:policy`)만 가능하고 **활성 프로젝트에 저장**되어
  다음 기동·재활성화에도 유지된다
- **LLM Decision Log** — 프록시·진단의 모든 LLM 판정 기록. allow/block 필터, **캐시 적중률**
  (높을수록 룰 이관 효과 큼). 요청·판정·신뢰도·근거·모델·**프롬프트**·캐시 hit 표시.
  프롬프트 열은 그 판정이 어느 정책에서 나왔는지(`strict`/`balanced`/`permissive`/`custom`,
  툴팁에 지문) 보여준다 — 정책을 바꾼 전후를 로그에서 구분할 수 있다

## HITL(사람 개입) 설계
후보는 **제안일 뿐** — 리더가 검토·승인해야 룰이 됩니다. 채택 후엔 동일 요청을 LLM 없이
결정론적으로 판단합니다. 이름 중복은 거부, 채택은 감사에 기록됩니다.

## 주요 액션 → API

| 액션 | 엔드포인트 | 권한 |
|---|---|---|
| 룰 채택 | `POST /api/rules/adopt` (`signature`) | 리더(`rule:promote`), 감사 기록 |
| 판단 프롬프트 정책 변경 | `POST /api/judge-prompt` (`preset`, `custom`) | 리더(`llm:policy`), 감사 기록 |

조회: `/api/llm-decisions` · `/api/rule-candidates` · `/api/rules` · `/api/judge-prompt`

## 판단 프롬프트와 캐시 (이슈 #53)

프롬프트가 상수가 아니게 되면 **요청 시그니처만으로 만든 판정 캐시는 정책을 섞는다** —
permissive 프로젝트에서 allow 로 캐시된 항목이 strict 프로젝트로 전환한 뒤 그대로 재사용된다
(같은 프로세스·같은 전역 캐시). 그래서 캐시 키에 프롬프트 지문(sha256 앞 8자리)을 넣었다.
정책이 다르면 키가 다르고, 정책을 바꾸면 옛 항목은 자연히 미스가 된다(별도 무효화 없음).
`judge_prompt`/`judge_prompt_custom` 을 설정하지 않으면 `balanced` — **종전 하드코딩 프롬프트와
바이트 단위로 동일**하다(회귀 테스트 `TestBalancedPresetIsLegacyPrompt`).
