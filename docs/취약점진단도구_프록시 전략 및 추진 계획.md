> **기준 문서:** 「취약점진단도구 요구사항·아키텍처 정의서 v0.6」  
> **문서 목적:** 기준 문서와 중복되는 요구사항·모듈·데이터 모델 설명은 제외하고, 프록시 엔진 선택과 향후 한 달 동안 진행할 기반 작업만 정리한다.  
> **문서 성격:** 프록시 기술 의사결정 및 단기 추진 계획 별첨

## 1. 핵심 결론

기준 문서의 `mitmproxy addon 내장` 방향을 유지하여 **mitmproxy 기반 반자체 프록시**로 설계하는 것을 권고한다.

- TLS·HTTP 처리: mitmproxy 사용
- 자체 구현: 스코프, 안전 정책, 마스킹, 엔드포인트 추출, Rule·LLM 판단 파이프라인
- 프록시 엔진: 초기에는 mitmproxy 단일 구현
- 확장성: `ProxyEngine` 인터페이스만 교체 가능하도록 얇게 유지
- Burp Suite: 주 엔진이 아닌 수동 심층진단·보조 도구 연동 대상으로 분리
- goproxy: Python 배포가 불가능하거나 단일 실행파일이 필수가 될 때 재검토
- 완전 자체 프록시: 개발·검증·유지보수 부담 때문에 제외

핵심 원칙은 다음과 같다.

> **인터페이스는 향후 교체를 고려하되, 실제 프록시 엔진 구현은 하나만 유지한다. 여러 보안 도구의 활용은 `ProxyEngine`이 아니라 `ToolAdapter` 계층에서 해결한다.**

## 2. 반자체 프록시의 범위

반자체 프록시는 소켓, TLS, HTTP 파서를 처음부터 직접 만드는 것이 아니다. 검증된 엔진을 사용하고 이 프로젝트에 필요한 판단 파이프라인을 자체 구현하는 방식이다.

| 구분 | 담당 영역 |
|---|---|
| mitmproxy | HTTP/HTTPS 연결, TLS 인터셉트, 동적 인증서, 요청·응답 파싱, 연결 관리 |
| 자체 모듈 | 스코프 강제, 위험 요청 차단, 민감정보 마스킹, 엔드포인트 수집, Rule·LLM 판단, 프로젝트 저장소 연동 |

처리 구조는 다음과 같다.

```mermaid
flowchart LR
    CLIENT["브라우저·테스트 단말"] --> ENGINE["mitmproxy"]
    ENGINE --> ADAPTER["엔진 어댑터"]
    ADAPTER --> MODEL["공통 Request/Response 모델"]
    MODEL --> PIPELINE["스코프·안전·마스킹·판단"]
    PIPELINE --> TARGET["대상 서버"]
    TARGET --> COLLECT["엔드포인트·증적 수집"]
    COLLECT --> STORE["프로젝트 저장소"]
```

mitmproxy의 Flow 객체는 어댑터 내부에서만 사용하고, 나머지 모듈은 공통 요청·응답 모델에 의존하도록 설계한다. 이를 통해 후속 엔진 교체 가능성과 단위 테스트 용이성을 확보한다.

## 3. 프록시 엔진 비교

| 기준 | mitmproxy | Burp Suite | goproxy |
|---|---|---|---|
| 성격 | 확장 가능한 독립 MITM 프록시 | 완성된 보안 진단 제품 | Go 프록시 라이브러리 |
| 확장 방식 | Python addon | Java/Kotlin Montoya Extension | Go handler |
| 독립 플랫폼 구성 | 적합 | Burp 실행환경에 종속 | 적합 |
| 자체 파이프라인 결합 | 용이 | Burp API 범위 내 가능 | 자유도가 높음 |
| 기존 진단 기능 | 직접 개발·연동 필요 | 사이트맵·Repeater·Scanner 등 활용 가능 | 직접 개발·연동 필요 |
| 배포 고려사항 | Python 런타임 또는 번들 | Burp 설치·에디션·라이선스 | 단일 실행파일에 유리 |
| 초기 부담 | 비교적 낮음 | Burp 중심 구조 설계 필요 | 프록시 기반 기능 검증 부담 증가 |
| 적합한 결과물 | 독립 사내 진단 플랫폼 | Burp 기반 사내 플러그인 | 단일 바이너리 프록시 제품 |

### 3.1 mitmproxy 권고 이유

- 기준 문서의 독립 프로젝트 서버·진단 엔진 구조와 잘 맞는다.
- 요청 전·응답 후 addon hook에 자체 판단 파이프라인을 연결하기 쉽다.
- Python 기반 LLM·데이터 처리 모듈과 결합하기 용이하다.
- TLS·HTTP 기반 기능을 재사용해 진단 기능과 데이터 흐름 설계에 집중할 수 있다.
- Burp 제품과 라이선스에 종속되지 않고 독립 프로그램으로 발전시킬 수 있다.

### 3.2 Burp를 주 엔진으로 사용할 경우

Burp를 선택하는 것이 유리한 경우도 있다.

- 최종 결과물이 독립 플랫폼이 아니라 Burp Extension인 경우
- 회사 진단 업무가 이미 Burp Professional을 중심으로 운영되는 경우
- 사용자별 필요한 라이선스가 확보된 경우
- 자체 프로젝트 서버보다 Burp 프로젝트와 사이트맵을 기준 데이터로 사용하려는 경우

현재 기준 문서의 목표는 독립 진단 플랫폼에 가까우므로 Burp를 주 엔진으로 사용하면 다음 문제가 생길 수 있다.

- 자체 프로젝트 저장소와 Burp 프로젝트의 역할 중복
- Burp 데이터 모델과 실행환경에 대한 종속
- 사용자별 설치·에디션·라이선스 관리
- 독립 UI와 Burp UI 사이의 사용자 흐름 분리

따라서 현재는 Burp를 다음 용도로 두는 것이 적절하다.

- 수동 심층진단
- Repeater 기반 재현
- Scanner 결과의 Finding 변환
- 선택 요청을 Burp로 전달하거나 결과를 가져오는 `ToolAdapter`

### 3.3 goproxy를 보류하는 이유

goproxy의 가장 큰 장점은 Go 기반 단일 실행파일 배포다. 그러나 현재 이 조건이 필수로 확정되지 않았다.

초기에 goproxy를 선택하면 인증서, 프로토콜 호환성, Replay, 오류 처리 등 프록시 기반 기능을 더 넓게 직접 검증해야 한다. 따라서 현재는 mitmproxy를 우선 사용하고 다음 조건이 확인될 때 재검토한다.

- 회사 환경에서 Python 런타임과 번들 실행파일 모두 배포 불가
- 단일 정적 바이너리가 필수 요구사항으로 확정
- mitmproxy의 성능 또는 구조적 제약이 실제 검증에서 확인

## 4. 기술 결정 기록 초안

### ADR-PROXY-001: 주 프록시 엔진 선택

**상태:** 제안

**결정:**

웹 1차 버전은 mitmproxy addon 기반 반자체 프록시로 설계한다. 실제 엔진 구현은 하나만 두고 `ProxyEngine` 인터페이스는 향후 교체 가능하도록 유지한다.

**선택 이유:**

- 독립 플랫폼 구조 유지
- 검증된 TLS·HTTP 엔진 재사용
- 자체 판단 파이프라인 결합 용이
- Python 기반 코어·LLM 모듈과의 정합성
- 초기 기술 위험과 구현 부담 감소

**미채택 대안:**

- Burp Suite: 독립 플랫폼보다 Burp Extension 구조에 적합
- goproxy: 단일 바이너리 요구가 확정되지 않은 상황에서 추가 검증 부담이 큼
- 완전 자체 구현: 진단 기능과 무관한 네트워크 기반 개발 비용이 과다

**재검토 조건:**

- Python 배포 불가
- 단일 정적 바이너리 필수
- mitmproxy의 실측 성능 병목
- 구조적으로 해결할 수 없는 프로토콜·기능 제약
- 프로젝트 목표가 Burp Extension으로 변경

## 5. 향후 한 달 추진 목표

- 프록시와 코어 모듈의 경계가 정의되어 있음
- 공통 요청·응답 모델과 핵심 인터페이스 초안이 있음
- mitmproxy 기반 데이터 흐름의 기술적 가능성이 검증되어 있음
- 후속 작업과 미해결 리스크가 정리되어 있음
- 다른 사람이 문서와 PoC를 보고 작업을 이어갈 수 있음

## 11. 최종 정리

기준 요구사항 문서의 전체 방향은 유지한다. 이 별첨에서 추가로 제안하는 핵심은 다음 두 가지다.

### 프록시 전략

> **mitmproxy 단일 엔진 기반 반자체 프록시를 우선 채택한다. mitmproxy는 TLS·HTTP 처리만 담당하고, 스코프·안전정책·마스킹·엔드포인트 추출·Rule·LLM 판단은 프록시 중립적인 자체 모듈로 분리한다. Burp는 수동 심층진단과 ToolAdapter 계층에서 활용하고, goproxy는 배포 제약이 확인될 때 재검토한다.**

### 향후 한 달 방향

> **전체 기능 구현보다 요구사항 범위, 기술 결정, 모듈 경계, 공통 데이터 계약과 리스크를 정리하고, mitmproxy 기반 핵심 데이터 흐름을 작은 PoC로 검증하여 후속 개발이 이어질 수 있는 기반을 남긴다.**
