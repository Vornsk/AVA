# 프록시 엔진 전략 비교분석 — 완전자체 vs 반자체 vs 기성품 + 단일/다중 엔진 결정

> 대상 문서: 「LLM 기반 웹/모바일 자동 취약점 진단 도구 요구사항·아키텍처 정의서 v0.6」의 §5.2(MITM 프록시)·§2.1(`ProxyEngine` 인터페이스) 검토용 별첨.
> 목적: "자체 프록시를 만든다면?"에 대한 (1) 세 가지 방식 비교, (2) 반자체 시 엔진 선택, (3) 단일 엔진 vs 다중(확장가능) 엔진 전략 결정.
> 성격: 본 정의서에 병합하지 않는 **독립 검토 문서**. 결론만 반영하고 싶을 때 §5.2/부록에 발췌.

---

## 0. 한 줄 결론 (TL;DR)

- **완전 자체(소켓·TLS부터)는 권장하지 않는다.** 비용의 대부분이 진단 가치와 무관한 TLS/HTTP2/3 인프라이고, 여기서 나는 버그는 곧 "인터셉트 누락 = 진단 구멍"이 된다.
- 현재 정의서의 "mitmproxy addon 내장" 결정은 사실상 이미 **반자체(엔진은 검증품 재사용 + 판단 파이프라인은 자체)**다. 방향은 옳다.
- **프록시 엔진(ProxyEngine)은 단일로 통일**하고, "여러 도구를 쓰고 싶다"는 욕구는 **엔진 계층이 아니라 `ToolAdapter`(심층 스캔 보조) 계층에서** 충족하는 것이 복잡도·일관성 면에서 유리하다.
- 단, **인터페이스(`ProxyEngine`)는 다중 구현을 상정해 얇게 유지**한다 — 배포 제약(폐쇄망 단일 바이너리)·성능 병목이 **실측**되면 그때 두 번째 엔진(Go 계열)을 추가할 수 있게. "인터페이스는 다중, 구현은 당분간 단수."

## 1. 용어 정리 — "자체 프록시"의 세 층위

논의를 흐리는 가장 큰 원인은 "자체 프록시"라는 말이 세 가지를 뭉뚱그리는 것이다. 먼저 분리한다.

| 방식 | 정의 | 대표 예 | 현 정의서 위치 |
|---|---|---|---|
| **완전 기성(off-the-shelf)** | 완성된 프록시/스캐너를 GUI·CLI 그대로 사용, 스크립팅·확장만 | Burp Suite, OWASP ZAP, Caido를 그대로 운용 | 심층 스캔 보조로만 언급(§5.2 말미, Burp) |
| **반자체(embed + custom pipeline)** | 검증된 TLS 인터셉트 **엔진을 라이브러리/addon로 재사용**하고, 판단 파이프라인·스코프·마스킹·엔드포인트 추출은 **자체 구현** | **mitmproxy addon**, goproxy 위 자체 훅 | **현 결정이 여기다** (§5.2 "addon에 룰엔진·LLM 내장") |
| **완전 자체(from scratch)** | 소켓·TLS 핸드셰이크·동적 인증서·HTTP 파서까지 직접 | Go(`crypto/tls`)·Rust(`rustls`)로 신규 구현 | 미채택 |

**핵심 통찰:** 정의서가 프록시에 요구하는 가치 — 스코프 강제, 전송 전 판단 파이프라인(Rule→LLM), 엔드포인트 추출, 토큰 최소화·마스킹, dedup·캐싱 — 은 **전부 애플리케이션(파이프라인) 계층**이다. 어느 방식을 택하든 이 코드는 **똑같이** 짜야 한다. 따라서 방식 선택의 실질 차이는 오직 하나 — **TLS MITM 엔진을 재사용할 것이냐, 다시 만들 것이냐**이다.

## 2. 세 방식 비교표

평가축은 이 프로젝트의 요구(폐쇄망 배포·가용성·감사·다중신원·모바일 확장)에 맞춰 가중했다.

| 평가축 | 완전 기성 (Burp/ZAP 그대로) | **반자체 (엔진 재사용 + 자체 파이프라인)** | 완전 자체 (from scratch) |
|---|---|---|---|
| **TLS MITM 성숙도**(동적 인증서·TLS1.3·HTTP2/3·WS) | ◎ 최상(수년 검증) | ◎ 엔진에 위임 → 최상 | ✕ 직접 구현, 엣지케이스 지뢰밭 |
| **판단 파이프라인 통제**(inline Rule→LLM, 별도 왕복 없음) | △ 확장 API 한계 내에서만 | ◎ addon 훅에서 네이티브 통제 | ◎ 완전 통제(단 직접 구현) |
| **스코프 강제·마스킹 결합도** | △ 도구 모델에 종속 | ◎ 훅 진입점에서 하드 강제 | ◎ 완전 통제 |
| **개발 비용(초기)** | ◎ 낮음 | ○ 중간(파이프라인만) | ✕ 매우 높음 |
| **유지보수 비용**(프로토콜 최신화) | ◎ 벤더가 부담 | ○ 엔진 업스트림이 부담 | ✕ 전부 자가 부담(HTTP/3 등) |
| **배포(폐쇄망)** | △ 라이선스·설치 부담(Burp Pro 등) | ○ 엔진에 따라 다름(§5) | ◎ 단일 바이너리 설계 가능 |
| **성능·동시성 튜닝** | △ 제한적 | ○ 엔진 한도 내 | ◎ 자유(단 직접) |
| **LLM·룰엔진 통합 용이성** | △ 확장 SDK 종속 | ◎ 호스트 언어 자유(Python/Go) | ◎ 자유 |
| **감사·재현성**(§3 Evidence 요구) | △ 도구 로그 포맷에 맞춤 | ◎ 스키마를 자체 설계 | ◎ 자체 설계 |
| **진단 커버리지 리스크** | 낮음(검증품) | 낮음(엔진 검증품) | **높음**(엔진 버그=구멍) |
| **벤더/라이선스 종속** | 높음(특히 Burp 상용) | 낮음(대개 OSS) | 없음 |
| **인증서 핀닝 대응** | 별도 우회 필요 | 별도 우회 필요 | 별도 우회 필요 |

> 핀닝은 세 방식 모두 동일하게 **CA 신뢰만으로는 못 뚫는다**. 정의서 FR-2.9 그대로 별도 우회 도구 영역이며, 방식 선택과 무관하다.

**판정:** 완전 자체는 "진단 커버리지 리스크 高 + 유지보수 高"라는 두 치명타 때문에 폐쇄망 단일 바이너리라는 **단 하나의 강한 이유**가 없으면 정당화되지 않는다. 완전 기성은 파이프라인 통제·감사 스키마·라이선스에서 이 프로젝트의 핵심 요구와 어긋난다. → **반자체가 기본값.** (현 정의서 결정과 일치.)

## 3. 반자체 시 엔진 후보 비교

"반자체로 간다면 어떤 프록시(엔진)를 택할 것인가." 임베드/훅 가능한 엔진 위주로, 이 프로젝트 요구에 대입해 평가한다.

| 엔진 | 언어 | HTTP/2·3·WS | 임베드/훅 모델 | 배포 | LLM·룰 통합 | 라이선스 | 이 프로젝트 적합도 |
|---|---|---|---|---|---|---|---|
| **mitmproxy** (addon) | Python | HTTP/1·2 성숙, **HTTP/3 정식(v11+)**, WS 지원 | `requestheaders`/`request`/`response` 훅에서 네이티브 실행 | Python 런타임 필요(PyInstaller로 번들 가능하나 무거움) | ◎ 최상(LLM SDK·룰 파이썬 생태계) | MIT | **◎ 1순위** — 훅 모델·프로토콜·문서 모두 최상 |
| **goproxy** (elazarl) | Go | HTTP/1 견고, **HTTP/2 제한적**, WS 기본 | `OnRequest/OnResponse` 핸들러 | ◎ **단일 바이너리** | ○ Go 생태계(LLM SDK 성숙 중) | BSD-3 | ○ 2순위 — **단일 바이너리·성능**이 필수일 때 |
| **martian** (google) | Go | HTTP/1 중심, HTTP/2 MITM 제한적 | modifier 체인 | ◎ 단일 바이너리 | ○ Go | Apache-2.0 | △ API 테스트/모바일 지향, 갱신 완만(v3.2.x) → 신규 채택 매력 낮음 |
| **Burp Suite** | Java(엔진) | ◎ 최상 | Montoya API 확장(Java), 상용 Pro 필요 | ✕ 무겁고 상용 | △ Java 확장 SDK 종속 | 상용 | △ **엔진 임베드가 아니라 "보조 스캐너"**로 쓰는 게 맞음(§4) |
| **OWASP ZAP** | Java | ◎ 양호 | daemon+REST API, add-on(Java) | △ JRE 필요, 무거움 | ○ REST로 외부 오케스트레이션 | Apache-2.0 | △ 무료 스캐너 보조로 유용, 엔진 임베드엔 부적합 |
| **Caido** | Rust | ◎ 양호 | workflow·plugin(JS), GUI 지향 | △ open-core 상용 | △ 플러그인 모델 종속 | open-core | △ 최신 GUI 대안, **라이브러리 임베드 모델 아님** |
| **완전 자체** | Go(`crypto/tls`)/Rust(`rustls`) | 직접 구현 | 완전 자유 | ◎ 단일 바이너리 | ◎ 자유 | 자체 | △ 배포 요구가 압도적일 때만 |

### 3.1 후보별 짧은 판단

- **mitmproxy** — 반자체의 사실상 표준 선택. 훅 지점(전송 전 인터셉트 = 판단 파이프라인 자리)이 정확히 요구와 맞고, HTTP/3까지 정식 지원하며, addon 단에서 마스킹·스코프·토큰최소화를 한 곳에 모을 수 있다(FR-2.3·§8 마스킹 일원화와 정합). **폐쇄망에서 Python 런타임을 배포할 수 있다면 1순위.**
- **goproxy(Go)** — 유일하게 mitmproxy와 진지하게 경합하는 이유는 **단일 정적 바이너리**다. Python·의존성 없이 하나의 실행파일로 폐쇄망·DRM 환경에 떨군다. 대가는 **HTTP/2 인터셉트가 제한적**이고 프로토콜 엣지케이스 성숙도가 mitmproxy보다 낮다는 것. "배포 단순성 > 프로토콜 커버리지"일 때만.
- **martian** — 굳이 신규로 택할 이유가 약하다(모바일/API 프록시 지향, 갱신 완만). goproxy로 대체 가능.
- **Burp/ZAP** — **엔진으로 임베드하지 말 것.** 이들은 "판단 파이프라인을 얹는 얇은 엔진"이 아니라 그 자체가 완성된 스캐너다. 정의서도 이미 Burp를 "심층 스캔 보조"로 분리해 뒀다(§5.2 말미). → **§4의 `ToolAdapter`로 붙이는 게 정답.** 마침 이 세션에는 `burp-mcp-bridge`가 이미 연결돼 있어, Burp를 오케스트레이션 계층에서 보조 스캐너로 호출하는 그림이 자연스럽다.
- **Caido** — GUI 지향 최신 대안. 팀이 수동 심층 점검에 쓰기 좋지만, 우리 파이프라인의 **임베드 엔진**으로는 맞지 않는다. 필요하면 보조 도구 취급.

## 4. 핵심 결정 — 단일 엔진 vs 다중(확장가능) vs 자체 단일

사용자 질문의 심장부. 세 선택지를 그대로 놓고 본다.

### 4.1 세 선택지

1. **단일 자체 프록시만** (하나 만들어 그것만) — 완전 자체 or 반자체 엔진 1개 고정, 추상화 없음.
2. **단일 반자체 엔진 고정** (mitmproxy 하나, `ProxyEngine` 추상화는 얇게만).
3. **다중 엔진 확장 가능** (`ProxyEngine`를 두껍게, 여러 프록시 교체·병용).

### 4.2 먼저 함정 하나 — "프록시 엔진"과 "스캔 도구"를 구분하라

"여러 프록시 도구를 쓸 수 있게 하고 싶다"는 욕구는 대부분 **잘못된 계층에 배치된 요구**다. 두 계층은 성격이 다르다.

| 계층 | 역할 | 다중성 | 정의서 위치 |
|---|---|---|---|
| **인터셉트 엔진(`ProxyEngine`)** | 실트래픽을 가로채 **판단 파이프라인이 사는 곳**. 스코프·마스킹·토큰최소화가 여기 결합 | **단일이 유리** — 판단 로직·증적 스키마·마스킹이 한 엔진에 묶여야 일관 | §5.2 `mitm-proxy` |
| **심층 스캔 보조 도구(`ToolAdapter`)** | sslscan·tshark·sqlmap·**Burp/ZAP** 등 결과를 finding으로 정규화 | **다중이 정답** — 이미 플러그인·다중 설계 | §5.3 FR-3.4, `tool-adapters` |

즉 **"여러 프록시를 쓰고 싶다"의 90%는 `ToolAdapter` 계층에서 이미 충족된다.** Burp로 심층 스캔하고 싶으면 엔진을 Burp로 바꾸는 게 아니라 Burp를 보조 도구로 붙이면 된다. 판단 파이프라인이 사는 인터셉트 엔진은 하나로 두는 편이, 마스킹·스코프·증적·룰이관(§5.6)의 **일관성과 감사성**을 지킨다.

### 4.3 다중 엔진(선택지 3)의 실제 비용

두 엔진을 동시에 "교체 가능"하게 진지하게 유지하면 다음을 감당해야 한다.

- **추상화의 최소공배수 수렴** — `ProxyEngine` 인터페이스가 mitmproxy와 goproxy 양쪽이 공통 지원하는 기능으로 수렴한다. mitmproxy의 강력한 훅을 못 쓰게 될 수 있다.
- **파이프라인 이식 비용** — 훅 모델·요청/응답 표현·스트리밍 처리 방식이 엔진마다 달라, 판단 스테이지·마스킹을 엔진별로 다시 검증해야 한다.
- **테스트 매트릭스 N배** — 인증 크롤링·핀닝 감지·인증서 자동설치(FR-2.6~2.9)·다중신원(FR-3.6)을 **엔진 수만큼** 재검증.
- **증적 재현성 리스크** — 이행점검 replay(§5.5)는 "판정 당시 컨텍스트"에 의존한다. 엔진이 다르면 재현 미세차가 생겨 diff/회귀(§5.4)를 오염시킬 수 있다.

이 비용은 대부분의 팀에서 **얻는 이득(벤더 회피·상황별 최적)보다 크다.** 특히 웹 1차 범위에서는.

### 4.4 그래서 권고 — "인터페이스는 다중을 상정, 구현은 당분간 단수"

정의서 §2.1에 `ProxyEngine`을 이미 플러그인 인터페이스로 정의해 둔 것이 정답의 절반이다. 나머지 절반은 **그 인터페이스를 얇게 유지하되, 실구현은 1개만** 두는 것.

구체 실천:

1. **엔진은 mitmproxy 단일**로 시작(Python 배포 가능 시). 판단 파이프라인·스코프·마스킹·엔드포인트 추출을 addon 훅에 얹는다 = 현 정의서 결정 유지.
2. **판단 파이프라인 로직을 프록시-중립 모듈로 분리** — addon은 "훅에서 우리 모듈을 호출"하는 얇은 껍데기로. 이게 실질적 확장성의 핵심이다. 엔진을 바꿔도 판단 로직·룰엔진·마스킹·LLM 게이트웨이가 그대로 재사용된다. (정의서 다이어그램이 이미 `mitm-proxy`(엔진)와 core 판단 모듈을 분리한 방향과 정합.)
3. **`ProxyEngine` 인터페이스는 mitmproxy 전용 기능에 의존하지 않도록** 최소 계약(intercept·전송보류·응답콜백·스코프훅)으로 정의. 단, 지금 두 번째 구현을 만들지는 않는다.
4. **"여러 도구" 욕구는 `ToolAdapter`로** — Burp/ZAP/sslscan/tshark를 보조 스캐너로. (Burp는 이미 `burp-mcp-bridge` 연결됨.)
5. **두 번째 엔진(goproxy 등)은 트리거가 실측될 때만 추가** — 아래 트리거 참조.

### 4.5 두 번째 엔진을 추가해도 되는 트리거(그 전엔 하지 말 것)

- 폐쇄망/DRM 환경에서 **Python 런타임 배포가 실제로 금지**되어 단일 정적 바이너리가 필수로 확정됐을 때 → goproxy(Go) 엔진 추가.
- mitmproxy에서 **성능 병목이 실측**되고(대량 동시 트래픽), 튜닝으로 해결 안 될 때.
- mitmproxy가 **구조적으로 막는 특정 요구**가 확인됐을 때(드묾).

이 트리거 중 하나라도 실제로 부딪히기 전에는, 다중 엔진은 **YAGNI(You Aren't Gonna Need It)**다. 인터페이스만 열어두는 것으로 충분하다.

## 5. 배포 시나리오별 권고 (미확정 변수)

권고는 "폐쇄망에서 Python 런타임을 배포할 수 있는가?" 하나에 크게 갈린다. 이 값이 아직 미확정이므로 두 분기를 모두 제시한다.

| 시나리오 | 엔진 선택 | 근거 |
|---|---|---|
| **A. Python 런타임 배포 가능**(가상환경/PyInstaller 허용) | **mitmproxy 단일** | 훅·프로토콜·문서·마스킹 통합이 최상. 대부분 이 경우로 충분. |
| **B. 단일 정적 바이너리 필수**(Python 불가, DRM/폐쇄망 엄격) | **goproxy(Go) 단일** 또는 mitmproxy를 PyInstaller로 번들 검증 후 채택 | Go는 단일 바이너리·성능 확보. 대가로 HTTP/2 인터셉트 성숙도 하락 감수. |
| **C. 지금은 A, 장래 B 가능성** | **mitmproxy로 시작 + `ProxyEngine` 얇게 유지** | 나중에 goproxy 구현을 "추가"만 하면 됨. 판단 로직은 중립 모듈이라 재사용. |

> 실무 권고: 대부분의 조직은 **C**가 안전하다. 지금 mitmproxy로 빠르게 검증하되, 판단 파이프라인을 엔진 밖 중립 모듈로 빼두면 B로의 전환 비용이 낮아진다.

## 6. 리스크 & 완화

| 리스크 | 완화 |
|---|---|
| mitmproxy Python 런타임이 DRM/폐쇄망 정책에 걸림 | 배포 형태를 **초기에 확정**(시나리오 A/B). 걸리면 goproxy 엔진으로 조기 전환. |
| 추상화가 새어 mitmproxy 전용 기능에 의존 | `ProxyEngine` 계약 리뷰를 코드리뷰 게이트로. 엔진 전용 API는 addon 껍데기 안에 격리. |
| 다중 엔진 유혹으로 조기 복잡화 | §4.5 트리거 없이는 2번째 엔진 금지. 인터페이스만 열어둠. |
| Burp를 엔진으로 오용 | Burp/ZAP는 `ToolAdapter`(보조 스캐너)로만. 판단 파이프라인은 얹지 않음. |
| 핀닝 대상에서 인터셉트 실패 | 방식 무관 한계. FR-2.9대로 감지·표시 + 별도 우회 도구 영역으로 분리. |
| 엔진 교체 시 이행점검 replay 재현 오차 | 증적 스키마(§3 Evidence)를 엔진 중립으로 고정. replay는 "저장된 요청 원문" 기준으로. |

## 7. 최종 권고 요약 (결정 트리)

```
Q1. 완전 자체(소켓·TLS부터)를 만들 이유가 있나?
   └─ 거의 없음 → 반자체로 간다. (완전 자체는 배포요구가 압도적일 때만, 그마저 goproxy로 대체 검토)

Q2. 반자체 엔진은?
   ├─ Python 배포 가능  → mitmproxy (1순위, 현 결정 유지)
   └─ 단일 바이너리 필수 → goproxy(Go)

Q3. 여러 프록시를 지원(확장가능)해야 하나?
   ├─ 인터셉트 엔진(ProxyEngine)  → 단일. 인터페이스만 다중 상정, 구현은 1개.
   └─ 심층 스캔 도구(ToolAdapter) → 다중. Burp/ZAP/sslscan/tshark를 여기로. (확장성은 여기서 확보)

Q4. 두 번째 엔진은 언제?
   └─ 배포제약·성능병목이 "실측"될 때만. 그 전엔 YAGNI.
```

**정리:** 하나의 검증된 반자체 엔진(mitmproxy, 배포제약 시 goproxy)으로 **단일화**하고, 다양성은 `ToolAdapter`에서 확보하며, `ProxyEngine` 인터페이스는 미래 교체를 위해 얇게 열어두되 지금 다중 구현하지 않는다. 이것이 복잡도·일관성·감사성·확장성의 균형점이다.
